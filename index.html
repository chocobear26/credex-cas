Produktdokumentation CredEx Phase 1 im Open Knowledge Format

Die Anforderungen von CredEx Phase 1 – Dokumentenupload über die eigene KI des Partners (Gruppe 6, CAS Business Analysis and Methods, ZHAW), geführt als offenes, maschinenlesbares Wissens-Bundle: Jedes Dokument sagt, was es ist, woraus es abgeleitet ist, wer es geschrieben hat und ob ein Mensch es freigegeben hat. Diese Seite erklärt, wie die Teile des Repositorys zusammenspielen. Das Ergebnis ist die Dokumentation CredEx Phase 1; der Code liegt auf GitHub. Grundlage ist das Beispiel okf-productdocumentation von Marcel Ronner.

This repository is step 2 of a two-step series. Step 1, okf-llm-wiki, shows the basics on a simple knowledge wiki. Here the same ideas are applied to the documentation of a software product.

The idea in one paragraph

Requirements documents usually go out of date, because every change has to be copied by hand into many places — and after a while nobody can say which document a statement came from, or whether anyone checked it. Here, every document carries that information in a small, standard label, and an AI agent called Jarvis helps with the requirements analysis: you tell it what should change; it works out which documents are affected, updates them in the right order, and records what it did. You stay in charge: nothing counts as approved until a person says so.

The label on every page

Each document starts with a short block of labels that people rarely see but tools read. It says what kind of document it is, which documents it was derived from (sources), who wrote it and when (generated), whether a person approved it (verified), and which parts of the domain it is about (tags). The labels follow an open standard, the Open Knowledge Format (OKF), so any other agent can read this documentation without special tools.

How well does the documentation follow that standard? Type /okf-check, and Jarvis goes through the standard’s 41 rules one by one and files a report next to the change requests in content/sources/. Old reports are never overwritten, so two of them show what got better in between — and a change request that fixes a finding points back at the report that found it.

The diagrams are written as text too, and drawn automatically when the site is built — so a picture can never disagree with the text it was drawn from.

The five parts

📄 The documentation

Plain text files in content/, together one OKF bundle: the domain model, business process, use cases, state chart, epics and user stories. One file per artifact, one folder per kind of artifact.

📝 The change requests

Every change is written down first, in content/sources/: what was asked, what it affects, and what was decided. The documents that change point back to it.

🧭 Jarvis and its instructions

Jarvis is the agent that helps with the requirements analysis. Text files tell it how to work: AGENTS.md for the general rules, .claude/rules/ for how each kind of artifact must look, and .claude/skills/ for step-by-step procedures. GitHub Copilot and Claude Code both read them.

✅ The checks

Small programs in scripts/ that catch mistakes a person would miss: a broken link, a missing label, a diagram that does not draw. If a check fails, nothing is published.

🌐 The website

A tool called Hugo turns the text files into the documentation website. Every time the main version on GitHub changes, the site is rebuilt and uploaded automatically.

How a change flows through it

  1. You ask for a change — for example “eingereicht wird nur ein vollständiger Antrag”.
  2. Jarvis analyses it, asks about anything unclear, and shows which documents it affects.
  3. Jarvis writes a change request into content/sources/, once you agree on the scope.
  4. Jarvis updates the documents from the inside out, starting with the domain model, because everything else depends on it.
  5. Jarvis drafts user stories for anything the system should now do differently, and shows them to you first.
  6. Jarvis records the version in the change log, stamps the OKF labels, and runs all the checks.
  7. You approve — and record it with one command, make verify, which adds a verified label. The agent is not allowed to do that step for you.
  8. The change goes to GitHub, and the website rebuilds itself.

Why the order matters

The documents build on each other. Change something on the left, and everything to its right may need to change too:

Domain Model→Business Process→Use Cases→State Charts & Epics→User Stories→Change Log

The documentation home page shows this chain in detail, with the IDs that connect the documents and a list of what to check after each kind of change.

Where the idea comes from

The labels come from the Open Knowledge Format. The way of working follows the LLM Wiki pattern: instead of searching raw notes every time a question comes up, an agent keeps a set of linked, up-to-date pages — and a person keeps the final say.
