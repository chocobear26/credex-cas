Produktdokumentation CredEx Phase 1 im Open Knowledge Format

Die Anforderungen von CredEx Phase 1 – Dokumentenupload über die eigene KI des Partners (Gruppe 6, CAS Business Analysis and Methods, ZHAW), geführt als offenes, maschinenlesbares Wissens-Bundle: Jedes Dokument sagt, was es ist, woraus es abgeleitet ist, wer es geschrieben hat und ob ein Mensch es freigegeben hat. Diese Seite erklärt, wie die Teile des Repositorys zusammenspielen. Das Ergebnis ist die Dokumentation CredEx Phase 1; der Code liegt auf GitHub. Grundlage ist das Beispiel okf-productdocumentation von Marcel Ronner.

Die Idee in einem Absatz

Anforderungsdokumente veralten meist, weil jede Änderung von Hand an vielen Stellen nachgezogen werden muss – und nach einer Weile weiss niemand mehr, woher eine Aussage stammt oder ob sie jemand geprüft hat. Hier trägt jedes Dokument diese Information in einem kleinen, standardisierten Etikett, und ein KI-Agent namens Jarvis hilft bei der Anforderungsanalyse: Die Gruppe sagt, was sich ändern soll; Jarvis ermittelt, welche Dokumente betroffen sind, führt sie in der richtigen Reihenfolge nach und hält fest, was er getan hat. Entscheiden und freigeben tut ein Mensch.

Das Etikett auf jeder Seite

Jedes Dokument beginnt mit einem kurzen Block, den Menschen selten sehen, Werkzeuge aber lesen: welche Art von Dokument es ist, woraus es abgeleitet ist (sources), wer es wann geschrieben hat (generated), ob ein Mensch es freigegeben hat (verified) und welche Fachklassen es betrifft (tags). Das Etikett folgt einem offenen Standard, dem Open Knowledge Format (OKF); jeder andere Agent kann die Dokumentation ohne Spezialwerkzeug lesen.

Wie gut die Dokumentation den Standard einhält, prüft /okf-check gegen 41 Regeln und legt den Bericht neben die Change Requests in content/sources/. Berichte werden nie überschrieben.

Auch die Diagramme sind Text – PlantUML, BPMN und D2 – und werden beim Bauen gezeichnet. Ein Bild kann deshalb nie vom Text abweichen, aus dem es entsteht.

Die fünf Teile

📄 Die Dokumentation

Textdateien in content/, zusammen ein OKF-Bundle: von der Ausgangslage über Fachklassenmodell, Soll-Prozess, Use Cases und Stories bis zu Anforderungen, MCP-Schnittstelle, Prototypen und Validierung.

📝 Change Requests und Entscheide

Jede Änderung wird zuerst in content/sources/ aufgeschrieben, jeder Teamentscheid in content/decisions/. Die geänderten Dokumente verweisen darauf.

🧭 Jarvis und seine Anweisungen

AGENTS.md enthält die allgemeinen Regeln, .claude/rules/ die Form jedes Artefakttyps, .claude/skills/ die Abläufe. GitHub Copilot und Claude Code lesen dieselben Dateien.

✅ Die Prüfungen

Programme in scripts/ finden, was ein Mensch übersieht: einen kaputten Link, ein fehlendes Etikett, ein Diagramm, das nicht zeichnet, eine Anforderung ohne Story. Schlägt eine Prüfung fehl, wird nichts veröffentlicht.

🌐 Die Website

Hugo macht aus den Textdateien die Website. Bei jeder Änderung auf GitHub wird sie neu gebaut und veröffentlicht.

Wie eine Änderung durchläuft

  1. Die Gruppe verlangt eine Änderung – zum Beispiel «eingereicht wird nur ein vollständiger Antrag».
  2. Jarvis analysiert sie, fragt nach, was unklar ist, und zeigt, welche Dokumente betroffen sind.
  3. Jarvis schreibt einen Change Request nach content/sources/, sobald der Umfang klar ist.
  4. Jarvis führt die Dokumente von innen nach aussen nach, zuerst das Fachklassenmodell, weil alles andere darauf aufbaut.
  5. Jarvis entwirft User Stories für alles, was das System nun anders tun soll, und legt sie zuerst vor.
  6. Jarvis hält die Version fest im Change Log, stempelt die Etiketten und lässt alle Prüfungen laufen.
  7. Ein Mensch gibt frei – mit make verify oder auf GitHub mit «Freigabe erfassen». Der Agent darf das nicht.
  8. Die Änderung geht auf GitHub, und die Website baut sich neu.

Warum die Reihenfolge zählt

Die Dokumente bauen aufeinander auf. Was links ändert, kann alles rechts davon ändern:

Fachklassenmodell→Soll-Prozess→Use Cases→Zustände & Epics→User Stories→Anforderungen→Rückverfolgung

Die Startseite der Dokumentation zeigt die Kette im Detail, mit den IDs, die die Dokumente verbinden.

Woher die Idee stammt

Das Etikett stammt aus dem Open Knowledge Format, die Arbeitsweise aus dem LLM-Wiki-Muster, das Repository aus dem Lehrbeispiel okf-productdocumentation von Marcel Ronner (CAS Business Analysis and Methods, ZHAW).
